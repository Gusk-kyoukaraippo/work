# Excelゲート実用版の設計案

更新日：2026-09-20

状態：目標との整合性を再検討した設計案。ここに示すAPI、共通部品、組み込み手順は未実装。実用版の完成を示す文書ではない。

## 再検討の結論

前案は基本構成としては目標と合うが、「既存HTMLの改修負担を最小限にした実用版」を達成したとは評価できない。特に、共通APIを3関数に見せても、その中で初期化・自動保存・全編集経路を改造するなら、組み込み負担は減ったことにならない。

| ユーザーの目標 | 評価 | 必要な修正・確認 |
| --- | --- | --- |
| 共有配布・file://・Excelを利用 | 方針は適合、基本方式に実環境の動作実績あり | 許容された一時実行コピー方式を使い、共通側が起動とファイル配置を担当する |
| 排他機能を追加 | 正式データの更新排他として適合 | 権利の取得・保存時の再確認・Excel終了による解放を一続きに定義する |
| 保存機能を追加 | 基本方式に実績あり、実用品質は未達 | 最終保存失敗時の状態を是正し、再試行・再起動・管理者復旧を検証する |
| HTMLの改修負担を最小化 | 未達 | 必須機能を絞り、初期化と自動保存を含む実際の差分で評価する |
| PoCから実用版へ移行 | 未達 | 二つの異なるアプリ、二台の実機、障害からの復旧、配布・更新まで確認する |

MVPの全機能を次版の必須仕様として継承しない。名前入力等を残す場合も、共通部品の設定として扱う。アプリ作者へ保存管理の実装を移植させないことを優先する。

## 目的と判断基準

共有フォルダに配布し、`file://` で利用する既存HTMLアプリに、Excelを使った排他制御と正式保存を追加する。HTMLアプリへの改修負担を最小限にすることを最優先とする。

MVP1〜3はユーザーの実環境で方式の成立を確認したPoCとして扱う。次版は、その動作実績を活かして、アプリごとに同じ連携処理を移植しなくてよい共通製品へ整理する。各MVPのファイルは検証記録として残す。

成功の基準は「一つのアプリが動いた」だけではない。構造の異なる二つ目のアプリを、共通Excel/VBAを変更せず、少量の接続コードと設定だけで組み込めることとする。

## 責任の分離

```mermaid
flowchart LR
  A[既存HTMLアプリ\n業務画面・計算・業務JSON] <-->|データと編集可否| B[アプリ別の小さな接続コード]
  B <--> C[共通JavaScript\n起動・保存操作・管理情報・案内]
  C <-->|起動データ／受け渡しJSON| D[共通Excel・VBA\n排他状態の確認・正式保存・復旧]
```

この図の矢印は論理的な受け渡しを示す。ブラウザとExcelの常時通信や、HTMLからのExcel直接操作を意味しない。

| 層 | 担当 | アプリ追加時の変更 |
| --- | --- | --- |
| 業務HTML | 入力、表示、計算、業務上の検証、業務JSON | データ入出力、必要な初期化・保存先の切替。閲覧対応を選ぶ場合は編集制御も必要 |
| 接続コード | 既存アプリの関数と共通APIを結ぶ | アプリごとに作成。業務処理全体にゲート対応条件を散在させない |
| 共通JavaScript | 名前入力、起動データ、保存用外枠、保存手順、再出力、終了案内 | 原則不要 |
| 共通Excel/VBA | 正式データ、編集セッション、保存可否の最終判定、整合性確認、保存と復旧 | 原則不要 |
| 配布設定 | アプリ名、HTML入口、アプリ識別子、データ版、同梱ファイル | 設定値だけ変更 |

業務JSONのキーや配列構造をExcel用に作り直さない。保存用の識別子、セッション、版番号などは共通側の外枠で保持する。業務JSON内に独自の `schemaVersion` がある場合も、共通外枠の版と混同しない。

## 必須機能と追加機能

必須にするのは、編集権のあるExcelからの起動、業務データの読み込みと取得、セッションに対応した受け渡しファイルの作成、Excelへの正式保存、失敗時の再開である。

他者が編集中でも同じHTMLで閲覧できることは、排他・保存に加わる利用機能であり、すべてのアプリへの無条件の組み込み義務にはしない。次のどちらを通常運用にするか、ユーザーへ確認中。既存MVPの閲覧機能を削除する決定はしていない。

| 利用方式 | 編集権がない人への動作 | HTML側の負担 |
| --- | --- | --- |
| 最小構成 | Excelで「ほかの利用者が編集中」と案内し、業務アプリの起動を止める | 閲覧専用モードの追加が不要 |
| 閲覧対応構成 | 正式保存済みデータを同じアプリで閲覧する | アプリ固有の編集禁止を接続する必要がある |

改修負担だけを基準にすれば最小構成を推奨する。閲覧が業務上必要なら閲覧対応構成を採用し、その改修を必要コストとして評価する。閲覧用データは正式保存済みのスナップショットであり、他者の編集中データのライブ表示とはしない。

精密な変更通知、途中保存と終了保存の使い分け、既存ボタンからの保存呼び出しは、初版の全アプリ必須条件にしない。MVPの保存形式を当面使う場合も、その区別は共通部品内に閉じ込める。

## アプリ側の最小接続契約

必須のデータ接点は読み込みと取得の二つにする。以下はAPIのたたき台であり、二つの関数の追加だけで全アプリの調整が終わるという意味ではない。

```js
ExcelGate.connect({
  load: function (payload) {
    // 既存のデータ反映処理を呼び、画面を更新する。
  },
  exportData: function () {
    // 未確定の入力と既存の業務検証を扱い、保存対象の業務JSONを返す。
    // 入力確定が必要なら、理由を示して出力を中止してよい。
    // 正式保存やダウンロードは行わない。共通側が担当する。
  }
});
```

両接点は同期処理とPromiseを返す非同期処理を受け付ける設計とする。例外・失敗・キャンセルでは、出力番号を進めず、編集終了にもせず、再操作できる状態へ戻す。取得成功後のスナップショットだけを共通側で検証し、保存用外枠へ包む。

「データを取得する」は単なる内部変数の参照とは限らない。未確定のダイアログや入力欄がある場合は、既存の確定処理を通すか、利用者に確定を求めて出力を中止する。画面上の入力を無視したまま終了画面へ切り替えてはいけない。

閲覧対応構成では `setReadOnly` の接点も必要になる。編集できないことを確認してから閲覧画面を利用可能にし、読込や閲覧設定の失敗時は編集可能な状態へ戻さない。

### 起動・保存先の契約

共通起動処理が、業務スクリプトより前に連携起動の情報を利用可能にする。アプリは最初のデータ選択箇所で、連携起動ならExcelデータを使い、単独起動なら従来の初期データを使う。この分岐と既存の永続化処理の切替は、アプリ固有の接続差分として数える。

共通側はアプリの準備完了とデータ反映の完了を待ち、その後に出力操作を有効化する。非同期で行う既存の復元や初期化が、後からExcelデータを上書きしないことまで確認する。初回利用で保存データがないことと、空オブジェクト等の保存済み業務データとは区別する。

読み込み失敗時に空データやサンプルデータへ黙って置き換えない。連携モードでは、既存の自動保存を正式保存として扱わず、従来の共有PC向け方針に従って業務データのブラウザ永続化を停止する。全ブラウザAPIを一律に差し替えて、どんなアプリにも対応したことにはしない。

名前入力、保存の種類、`sessionId`、`exportSequence`、`parentSaveDataId`、保存ファイル名、再ダウンロード、Excelへ戻る案内はアプリごとに実装させない。MVPの `workCopy` / `complete` を当面維持する場合も、共通側が処理する。

変更検知は標準フォームのイベントだけでは全アプリを扱えない。初版では正確な変更通知を全アプリの必須条件にせず、共通側は「出力済み」と「Excelに正式保存済み」を区別して表示する。変更状態が分からない場合は「変更なし」「すべて保存済み」と断定しない。精密な終了警告が必要なアプリだけ、変更通知を追加する。

### 共通画面の責任

名前入力・保存操作・終了案内は共通側で生成し、既存の `.site-header` や `main` を特定して書き換える仕様にしない。ゲート専用のDOM領域と識別子を持たせ、CSS、固定ヘッダー、ダイアログ、フォーカス、キーボード操作の衝突を二つの実アプリで確認する。衝突のたびに業務画面を共通テンプレートへ移植させる設計は不合格とする。

### 必ず確認するアプリ固有部分

- **初期データの優先順位**：Excel連携起動では、Excelからのデータを正式な起点にする。既存のlocalStorage復元やサンプル初期化で後から上書きしない。
- **既存の自動保存**：連携モードではブラウザ保存を正式保存と表示しない。共有PCでの業務データ保持の扱いは従来方針を維持し、勝手に常設キャッシュを追加しない。
- **閲覧制御を選ぶ場合**：入力欄だけでなく、追加・削除・ドラッグ・キーボード・外部操作APIなども対象にする。全ボタンを無効化して、検索や表示切替まで止めない。
- **関数へのアクセス**：データがクロージャ内にあるアプリでは、そのスコープ内に小さな接続箇所を設ける。外から任意の内部状態を自動取得できるとはしない。
- **既存のJSON入出力**：読込ボタンのファイル選択部分と、データ反映部分を分離して再利用する。既存の書出しがダウンロードまで行う場合は、データ取得部分を接続する。

### ゼロ改修の方式を標準にしない理由

アプリが元からJSONファイルの読み込みと出力を持つなら、Excelとの手動ファイル交換だけで、アプリを無改修にすることはできる。しかし業務JSONだけでは、同じ形式の別ブックや古い編集作業から出たファイルを区別できない。Excel側で現在のセッション情報を後付けしても、出力元の証明にはならない。

初版の標準は、小さな接続と共通JSによる保存用外枠の生成にする。任意のJSONを取り込む復旧操作は、通常保存と別の管理者向け手順にする。

## 排他と保存の境界

一つの共有データに対して一つの共有ブックを使い、作業中はそのブックを開いておく。実環境のファイル排他とブックの読み取り専用状態を利用する。ローカルに複製したブックを別の編集権として扱う運用にはしない。

通常手順は「共有Excelを開く → HTMLで編集 → 受け渡し用に出力 → Excelで正式保存 → Excelを閉じる」とする。保存完了やセッション解除だけではファイル排他が解放されたと扱わず、共有ブックを閉じる地点で次の人へ編集権を返す。

正本の場所と、別名保存・複製・復元したブックの扱いを配布設定と導入手順で定義する。現MVPが複製の利用を技術的に阻止しているとは扱わない。サポート対象は利用者全員が同じ正本を使う構成とし、パスの別表現を含む正本確認方法は実装前に固定する。

共通VBAは起動時だけでなく、取り込み時にも読み取り専用状態、現在のセッション、データ識別子、保存順を確認する。状態を確認できない場合は正式保存を許可しない。

Excelを閉じても、ブラウザの古い画面が残る可能性がある。排他の最終保証は「有効な編集権を持つExcelだけが正式データを更新できる」こととする。古い画面で操作できてしまっても、その出力を新しいセッションへ無条件に取り込まない。画面を閉じる処理だけを排他の根拠にしない。

HTMLからのJSON出力と、Excelへの正式保存は異なる段階である。正式保存完了を確認する経路がないHTMLでは、ダウンロードした時点で「Excelへ保存済み」と表示しない。

初版ではMVPの受け渡し経路と保存整合性の仕組みを土台にする。アプリへの組み込み負担の削減と、保存プロトコルの大幅変更を同時に行わない。再利用する保存処理も、異常終了・再実行・保存失敗時の状態を改めて確認する。

### 再利用前に修正する保存失敗時の問題

コードレビューでは、`MVP3rd/vba/utf8/Mvp2Storage.bas` の338〜351行で、メモリ上の履歴をSUCCESSにし、セッションと再開用メタ情報を消した後に、最後の `ThisWorkbook.Save` を実行している。この保存が失敗すると、取り込み失敗処理から呼ぶ画面更新が、completeの場合に「正式保存は完了しています」と表示し得る。同じExcel内での再試行もPREPARED状態を認識できない。

これはコード上の失敗経路の指摘であり、実機で障害を再現した結果ではない。先行保存したPREPAREDがディスクに残る可能性があり、直ちにデータが消えると断定はしない。

実用版では、保存前の状態を保持して失敗時に再開可能な状態へ戻すなど、最後のブック保存に失敗しても未完了表示・元データ・再開情報を維持する。「保存して終了」の経路では、成功表示と編集権の解放を永続化の成功確認後だけ行う。利用者が明示的に変更を破棄して終了する経路とは区別する。単に文言を変えるだけでは修正完了としない。

## 起動方式

ユーザーは「動けばどちらでもよい」と回答。共有フォルダ上のHTML原本を直接開く必須条件はないため、初版はMVP同様に一時実行用HTMLを生成するA方式を採用方針とする。コピー作成は共通側が担当し、アプリ作者に追加の配布手順を要求しない。

### A：共有配布から、一時実行用HTMLを生成する方式

現在のMVP3はHTMLテンプレートへデータを埋め込み、一時フォルダから `file://` で起動している。初版はこの動作実績を活かす。共有上のアプリ原本は書き換えず、正式データは共有上のExcelに保持する。

共通の配布・起動処理が起動データと共通部品を組み込み、相対パスを維持してアプリの必要ファイルを配置する。アプリ作者にMVPの大きな画面テンプレートへの移植や、VBAのファイルコピー処理の変更を要求しない。

アプリ固有のコードを自動解析して書き換える万能変換にはしない。明示的な接続箇所を設ける。複数ファイル構成、初期化順、厳格なCSPなど、対応範囲を検証して決める。

### B：共有フォルダ上のHTMLそのものを直接開く方式（初版では採用しない）

共通の起動画面と業務アプリを別文書にし、明示的なメッセージ接続でデータを渡す構成などを検討する。この場合も、業務アプリ内のデータ取得・反映には接続コードが必要。

`file://` の文書同士は、同じフォルダでも同一オリジンとは限らない。iframeの中へ外から自由にアクセスして無改造で接続できる前提にはしない。`postMessage` を使う候補は、対象ブラウザと共有パスで動作を確認し、送信元ウィンドウ・セッション・メッセージ内容を検証する。originが `null` であることだけを相手の識別に使わない。

この起動方式の違いは共通層で吸収し、業務アプリの接続契約は共通にする。

## 配布と更新

共通ソースと業務アプリを開発上は分離し、配布時に検証済みの組合せとしてまとめる。全アプリから共有上の「常に最新版」の共通JSを参照させて、一度の更新で全業務を変える運用にはしない。

配布設定には、表示名、HTML入口、アプリ識別子、業務データ版、必要ファイル、対応する共通部品の版を記録する。アプリを追加するたびにVBAソース内の定数や日本語タイトルを書き換える必要をなくす。

ランタイムにWebサーバーや新たな常駐プログラムを追加することは初版の前提にしない。初版の対象は、対象ブラウザでfile://動作し、JSONとして業務データを入出力できるアプリとする。サーバー必須のアプリや任意のWebアプリ全般への自動変換は含めない。

対象のWindows、Excel／JUST Calc、ブラウザと対応ファイル構成を、最初の実装前に固定する。PoCが旧ブラウザ互換を持つことと、将来も全アプリをその文法へ書き換えることは分けて判断する。共通部品を導入するだけで、業務アプリ自体のブラウザ非互換まで解消したとはしない。

## 実装順と完了条件

1. **適用範囲を固定する**：他者の編集中の閲覧要否、対象実機、保存対象JSONと未確定入力の扱いを決める。
2. **代表アプリで差分を出す**：進捗ボードを候補に、接続に必要な初期化・入出力・自動保存の変更を先に確認する。その差分に基づき共通部品を切り出す。
3. **二つ目で共通性を検証する**：異なる構造のアプリを同じ契約へ接続し、二つに共通する部分だけを共通製品にする。
4. **保存の異常系を是正する**：最終保存失敗を含め、元データと再開情報を保ち、失敗を成功表示しないことを確認する。
5. **配布と復旧を仕上げる**：設定とアプリ一式から配布し、バックアップから正本を復旧する管理者手順まで確認する。

### 改修負担を測る条件

各アプリについて、追加・変更した関数と理由を記録し、元HTMLとの差分を提示する。少ないAPI数や行数だけで達成としない。

- 業務JSON、画面構成、計算・検証の意味を維持できる。
- アプリ内の保存管理情報・セッション管理の実装はゼロ。共通部品を呼ぶだけである。
- アプリ追加時の共通VBAの変更はゼロ。設定値と同梱ファイルで対応できる。
- 基本構成の差分が、起動データ選択・データ反映・データ取得・既存の永続化処理の周辺に集中している。業務の各操作へExcel固有条件を足す必要があれば、共通設計を再検討する。
- 閲覧対応や精密な変更通知を選んだ場合の差分は、基本接続とは分けて記録する。
- 共通部品を更新しても、業務コードへの保存UIの再移植が不要である。

### 実用版としての最小受け入れ条件

- 二台から同じ正本を開き、正式保存できるのが一台だけである。通常の終了手順で、次の利用者へ編集権を返せる。
- Excel終了後の古いHTML、別セッション・別データのJSON、同じ出力の再取り込みを正しく扱う。
- 未確定入力を落とさず出力でき、取得失敗やキャンセルでは編集を続けられる。
- 受け渡しファイルの出力とExcelの正式保存完了を混同しない。
- 保存の各段階で通信断・保存失敗を発生させ、同じExcel内での再試行と再起動の双方で、確定済みデータを壊さず、版番号を二重に進めず、成功を誤表示しない。
- accepted等の保全された原本を使った管理者復旧を実演する。通常保存で古い出力を拒否する仕組みは弱めない。
- 二つのアプリをそれぞれ配布し、正式保存・終了・再起動後の復元まで往復できる。選択した構成に応じて閲覧制御も確認する。

アプリごとの確認は、データ往復、業務検証、未確定入力、初期データ優先順位、必要な閲覧制御を中心にする。保存の共通契約・異常系は共通基盤の試験としてまとめる。ただし各配布版では、対象アプリを含む実際の保存・再起動の往復を省略しない。

## 調査した根拠
