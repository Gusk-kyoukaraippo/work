# 0530時点の現状整理

## プロジェクトの大枠

老健アルボースの利用率低下に対して、原因分析と改善策の検討を進める。

現時点では、利用率低下の真因はまだ特定できていない。まずは、利用者データを最小限の形で集め、流入・滞在・流出のどこに問題があるのかを見える化する必要がある。

## 取り組む問題

アルボースの利用率が低下している。

具体的には、以下のような状況がある。

- アルボース入所者の利用率が低下している
- 利用率低下に対して、滞在者の入所延長などで対処している
- デイサービス利用者数も減っている
- 職員の休職・離職が多い
- 職員が離職・休職しても十分に補充されていない
- 職員同士の反目によるベテランの異動などもある
- その結果、営業活動も十分にできていない

## 背景仮説

アルボース全体に、いわゆる「殿様商売」的な姿勢が残っている可能性がある。

つまり、自分たちの都合に合う利用者が自然に来てくれればよい、という前提で運営されてきた可能性がある。

コロナ前、つまり6年以上前はそのやり方でも成立していた。しかし、現在は同じ前提では利用者が集まりにくくなっている可能性がある。

## 現在の課題認識

### 1. 真因がまだ不明

利用率低下の原因が、流入不足なのか、退所増加なのか、空床期間の長期化なのか、受入制限なのか、営業不足なのかはまだ明確ではない。

そのため、最初から特定の施策に飛びつくのではなく、利用率を構成する要素に分解して分析する必要がある。

### 2. データがサイロ化している

利用者データは存在しているが、分析に使える形で統合されていない。

既存システムや各部署には情報があるものの、すぐに横串で分析できる状態ではない。そのため、短期的には過去4か月分のデータを手入力で仮統合する方針を検討している。

### 3. 手入力には限界がある

手入力では、入力項目を増やすほど分析精度は上がるが、作業時間も増える。

そのため、初期段階では入力項目を絞り、継続可能な範囲で「流入・滞在・流出」が見えるデータを確保する方針。

### 4. 個人的な時間制約がある

正式な権限は明日までであり、プロジェクト自体は別部署へ移管される可能性がある。

そのため、明日までに何らかの成果を出す必要がある。単なる資料や分析メモだけでは、別部署に取り上げられる可能性があるため、アプリやプロトタイプの形で、自分が作った成果として残るものを作る必要がある。

## 初期データとして拾う項目

まずは、以下の項目を手入力で集める想定。

| 項目 | 目的 |
|---|---|
| 利用者ID | 個人識別。氏名よりID管理が安全 |
| 利用者種別 | 入所、ショート、通所、退所済みなどを分ける |
| 利用開始日 | いつから利用しているかを把握する |
| 利用終了日 | 退所・終了日を把握する |
| 利用区分 | 入所、ショート、デイ、通所リハなどを分ける |
| 入所場所 | 2F、3F、ユニットなど、場所別に見る |
| 流入元種別 | 病院、居宅、包括、家族、法人内などを分ける |
| 流出先・退所先 | 自宅、病院、特養、有料、死亡などを分ける |

今後、分析やアプリ機能のために追加候補となる項目は以下。

- 退所理由
- 担当者
- ケアマネ事業所
- 流入元名称
- 次アクション
- ロングステイ提案可能性

## 層別解析の初期案

利用率低下の原因をMECEに近づけて分析するため、以下の層別を検討している。

### 層別解析その1: 入居場所

- 2F
- 3F
- ユニット

### 層別解析その2: 担当者

相談員、営業担当、施設内担当など、誰が関与しているかで差を見る。

### 層別解析その3: 流入経路

病院、居宅、包括、家族、法人内サービスなど、どこから利用につながったかを見る。

### 層別解析その4: 流出経路

自宅、病院、特養、有料老人ホーム、死亡など、どこへ退所・移行したかを見る。

### 層別解析その5: ケアマネ事業所

どのケアマネ事業所から紹介が来ているか、または減っているかを見る。

## CRMとして見たいもの

老健の利用者CRMは、単なる利用者名簿ではなく、「誰に、いつ、何を提案すべきか」を可視化する仕組みと考える。

特に見たいものは以下。

- 現在どのサービスを利用しているか
- ショートからロングステイにつながりそうか
- 通所・訪問リハからショートや入所につながりそうか
- 退所後に再利用の可能性があるか
- ケアマネや病院MSWに確認すべき対象か
- 空床に対して条件が合う候補者がいるか
- 次に営業・相談すべき対象は誰か

## CRMに近い考え方

CRMという言葉に限定せず、以下の考え方を組み合わせる。

### パイプライン管理

相談、見学、申込、判定、入所調整、利用中、退所後フォローなど、利用者がどの段階にいるかを見る。

### ファネル管理

問い合わせから見学、申込、判定、利用開始までの歩留まりを見る。

### ライフイベント管理

入院、退院、ADL低下、認知症進行、主介護者の体調悪化、ケアマネ変更など、次の提案につながる変化を拾う。

### スコアリング

ショート利用頻度、家族疲弊、在宅困難コメント、入院歴、独居・老老介護などを点数化し、提案優先度を出す。

### Next Best Action

各利用者に対して、次に誰が何をするかを表示する。

例:

- 家族へロングステイ意向確認
- ケアマネへ在宅状況確認
- 退所後30日でフォロー
- 病院MSWへ退院予定確認
- 空床情報を紹介元へ共有

### 空床マッチング

空床条件と候補者条件を突き合わせ、今空いている床に合う候補者を出す。

## 検討中のアプリ案

真因分析だけでなく、短期間で何らかのアプリ成果物を作る必要がある。

検討したアプリ案は以下。

1. 利用率低下ダッシュボード
2. 空床インパクト分析アプリ
3. 流入元・紹介元営業アプリ
4. 退所理由・流出防止アプリ
5. ショートからロング転換候補アプリ
6. 退所後フォロー管理アプリ
7. 職員不足・受入制限の見える化アプリ
8. 仮説検証ボードアプリ

## 現時点の最有力案

最有力は、単独のCRMではなく、以下のような構成。

## アルボース利用率改善ダッシュボード

### 位置づけ

サイロ化している利用者情報を4か月分だけ仮統合し、利用率低下を流入・滞在・流出に分解して、重点的に営業・相談すべき対象を提示するプロトタイプ。

### 主な機能

- CSV取り込み
- 月別の入所数・退所数の可視化
- フロア別の利用状況の可視化
- 流入元別件数の可視化
- 退所先・退所理由別件数の可視化
- 重点課題の自動表示
- ロングステイ提案候補の表示
- 退所後フォロー候補の表示
- 営業すべき紹介元の表示
- 次アクション候補の表示

### この案の強み

- 真因分析とアプリ成果がつながる
- 「CRMを作った」よりも、利用率改善のための分析基盤として説明しやすい
- 既存システムの置き換えではなく、サイロ化した情報の仮統合プロトタイプとして位置づけられる
- 別部署へ移管されても、項目定義、分析ロジック、画面設計が成果として残りやすい

## 屋上屋批判への対応

既存システムがある以上、「それは既存システムで出せないのか」という批判は想定される。

そのため、アプリの位置づけは以下のようにする。

> 既存システムを置き換えるものではなく、サイロ化している利用者情報を4か月分だけ仮統合し、利用率低下の仮説検証に使うプロトタイプ。

この位置づけにより、二重管理ではなく、短期の仮説検証ツールとして説明する。

## 明日までに出したい成果

明日までの成果として、以下の3点セットを目指す。

1. データ項目定義書
2. 4か月分入力テンプレート
3. 利用率改善ダッシュボードのプロトタイプ

この3点があれば、単なる分析メモではなく、以下を示せる。

- 何をデータ化すべきか
- なぜその項目が必要か
- 入力すると何が見えるか
- 次に誰へ何を提案すべきか
- 真因分析をどう進めるか

## 現時点の説明文案

真因はまだ確定していないため、まず4か月分の最小データを仮統合し、流入・滞在・流出のどこに問題があるかを見える化するプロトタイプを作成する。

あわせて、次に営業・相談すべき候補も自動表示し、利用率改善のための具体的な次アクションにつなげる。
