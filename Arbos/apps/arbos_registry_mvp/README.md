# ALBOS 利用者・利用調整台帳 MVP

## 目的

ロング、ショート、デイに分かれている情報を利用者単位で一元表示し、利用履歴、今後の予定、フォロー担当、次回確認日、対応結果を同じJSONで管理するためのオフラインMVPです。

診療録・介護記録や既存システムを置き換えるものではありません。既存システムを利用実績・予定の正本とし、この台帳は横断的な利用関係、フォロー、調整記録の正本候補として扱います。

## 動作と保存の前提

- アプリ本体はCSS・JavaScriptを内包した `arbos-registry.html` 1ファイルです。
- HTMLは `file://` で直接開きます。Webサーバーとインターネット接続は不要です。
- 外部ライブラリ、外部画像、外部フォント、外部通信処理を使用しません。
- IndexedDB、File System Access API、localStorage、sessionStorageへ利用者情報を保存しません。
- JSONは通常のファイル選択から読み込み、編集内容は新しい全量JSONとして書き出します。
- 読込後のデータはブラウザのメモリ上だけにあります。画面を閉じると、書き出していない変更は失われます。

## 起動方法

1. `arbos-registry.html` を院内端末へ置きます。
2. ChromeまたはEdgeでファイルを直接開きます。Webサーバーは不要です。
3. 初回確認は画面の「デモデータで確認」または `arbos-registry-sample.json` の読込を使います。
4. 本運用では、中央管理している最新revisionの正本JSONを「JSON読込」のファイル選択から開きます。
5. 操作担当者を入力して編集し、画面右上の「JSON保存」で新しいJSONを書き出します。
6. 書き出したJSONを同じHTMLへ再読込し、検証に通ることと、利用者数・履歴件数・revisionを確認します。
7. 旧正本をバックアップしてから、確認済みの新JSONを中央管理場所の正本へ差し替えます。

## 保存方式の重要な制約

- 自動保存はありません。
- 元のJSONを直接上書きすることはできません。
- 保存すると `arbos_registry_r000001_YYYYMMDD_HHMMSS.json` のような新しい全量JSONがダウンロードされます。
- 「JSON保存」で書き出した直後のファイルは、まだ未検証の正本候補です。書き出し成功だけでは保存完了と扱いません。
- 書き出したJSONを再読込し、検証結果、利用者数、履歴件数、revisionを確認した時点で確認済みとします。
- 画面を閉じる前に、必ずJSONを書き出してください。
- 2人が同時に同じ正本を編集すると、片方の変更が失われる可能性があります。初期版は中央管理担当者1人が正本を排他運用してください。
- 旧正本は日付・リビジョン付きでバックアップし、通常のダウンロードフォルダを正本置場にしないでください。

## MVPの4画面

### 今週のフォロー

期限超過、本日、7日以内、期限未設定を確認し、担当者、期限、次の行動、対応結果、次回確認日を管理します。

### 利用者台帳

患者IDを正式キーに、ロング、ショート、デイの利用関係、直近実績、次回予定、未完了フォローを1利用者1行で横断表示します。

### 利用者詳細

基本情報、サービス利用関係、実績・予定、フォロー、電話・家族・ケアマネ等の対応記録を統合時系列で確認・更新します。

### データ管理

現在のdataset・revision・件数、元データの鮮度と連携状態、変更履歴を確認します。

## 初期版でできること

- 患者IDを正式キーとした1利用者1行の台帳
- ロング、ショート、デイの利用関係管理
- 利用実績、予定、取消の登録
- 利用実績・予定と対応記録をまとめた統合時系列
- ショート再利用、ロング相談、デイから初回ショート、退所後、3F候補等のフォロー管理
- 担当者、確認期限、次に行うこと、対応結果、次回確認日の記録
- データ鮮度と「連携済み／一部連携／未連携」の管理
- 利用者の休止・アーカイブ
- HTML内で行った変更の履歴

## JSON運用ルール

- `patientId` は文字列で保持します。先頭ゼロを削除しないでください。
- 同姓同名でも患者IDが異なれば別利用者です。氏名だけでは統合しません。
- 患者IDは登録後に画面から変更できません。
- 「予定情報未連携」と「連携済みだが次回予定なし」を区別します。
- 利用者、実績、フォロー、対応記録は削除せず、状態変更と履歴で残します。
- 操作前に画面右上へ操作担当者を入力してください。これは認証ではなく、作業記録用です。

## 既存分析DBから初期JSONを作る場合

`build_initial_registry_json.py` は既存のSQLite分析DBを、初回読込用JSONへ変換する準備用スクリプトです。ブラウザでの運用には使用しないため、実際の台帳は引き続き単一HTML＋JSONだけで動作します。

```sh
python apps/arbos_registry_mvp/build_initial_registry_json.py \
  --output /院内の管理場所/arbos_registry_initial.json
```

現在のデイ実績で患者IDが取れていない利用者は、自動的に氏名だけで統合せず、初期JSONから除外して件数を警告します。患者ID付きデータを取得して分析DBを更新した後、初期JSONを作り直してください。このスクリプトは運用開始前の初期作成専用であり、フォロー記録を持つ正本JSONへ上書き使用しないでください。

出力先に同名ファイルがすでにある場合、スクリプトは上書きせず終了します。必ず存在しない新しい出力パスを指定してください。このスクリプトは既存正本への追記・統合・更新には使用できません。

## 個人情報の扱い

このJSONは平文で個人情報を保持します。院内規程に従い、保存場所のアクセス権、端末暗号化、バックアップ、ダウンロード残骸の削除、持ち出し防止を別途管理してください。HTMLには外部通信処理、外部ライブラリ、外部画像、自動保存機能を含めていません。

## 現時点で含めないもの

- 複数人の同時編集
- ログイン・権限管理
- 改ざん防止された監査ログ
- 部屋割り、送迎、完全な予約管理
- 自動架電・自動連絡
- 医学的・介護的な受入可否の自動判定
- 既存システムへの書き戻し

## 中央運用に残る制約

初期版には共有サーバー、同時編集、ロック、競合検出、差分マージがありません。したがって、中央管理担当者1人が最新revisionの正本を受け渡し、編集、再読込確認、正本差替えまでを排他的に行う必要があります。複数部署が各自のJSONを編集する運用には対応していません。

## 検証

`tests/run-static-tests.mjs` は、単一HTMLであること、外部通信や禁止された保存APIを使っていないこと、埋込JavaScriptの構文、主要画面・フォーム、サンプルJSONの参照整合性を確認します。

```sh
node apps/arbos_registry_mvp/tests/run-static-tests.mjs
```
