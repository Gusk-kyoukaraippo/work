# 今回の目的整理

## 最終目的

他部署への引き継ぎになったとしても、自分をプロジェクトメンバーとして残す必要がある、と判断してもらうこと。

成果物そのものを自分のものとして守ることが目的ではない。  
アプリや資料の行方は重要ではなく、重要なのは「この人が関わり続けないと、このプロジェクトを十分に活かせない」と思わせること。

## 見せたい自分の価値

単にアプリを作れる人ではなく、以下を一体で考えられる人として見せる。

- 利用率低下という曖昧な問題を分解できる
- 流入・滞在・流出・空床という分析軸に整理できる
- 現場データを、検証可能な入力項目に落とし込める
- 入力されたデータから、次に見るべき仮説を出せる
- 仮説を、営業・相談・退所後フォローなどの次アクションに繋げられる
- その設計を、実際に動くプロトタイプとして形にできる

## 明日以降に残したい立ち位置

アプリ担当ではなく、企画・分析担当として残る。

具体的には、以下の役割を担う人として認識されることを目指す。

- 利用率改善プロジェクトの分析設計者
- データ項目と分析軸の設計担当
- 実データ投入後の仮説検証担当
- 現場情報を分析に翻訳する担当
- 改善アクションの優先順位を整理する担当

## 今日作るものの位置づけ

今日作るものは、完成版の業務システムではない。  
また、単なる集計表でもない。

位置づけは、以下の通り。

> アルボースの利用率低下について、真因を決め打ちせず、4か月分の最小データから流入・滞在・流出・空床のどこに問題があるかを検証するためのプロトタイプ。

このプロトタイプにより、実データを入力すれば、次にどこを確認し、誰に何を働きかけるべきかを議論できる状態にする。

## 明日見せたいメッセージ

このプロトタイプは、既存システムを置き換えるものではない。  
既存システムや各部署に分散している情報を、利用率改善という目的に沿って一時的に統合し、仮説検証に使うためのものである。

重要なのは、画面そのものではなく、以下の設計である。

- 何を入力すべきか
- なぜその項目が必要か
- 入力すると何が見えるか
- どの仮説を検証できるか
- 次に誰へ何を確認すべきか

この設計意図を理解して運用できる人が必要であり、自分はその役割を担える。

## 避けたい見え方

以下のように見えると弱い。

- 便利な表を作った人
- CSVを集計するアプリを作った人
- 画面を作れる人
- 一時的な補助作業者
- 引き継ぎ前に成果物を置いていく人

目指すべき見え方は、以下。

- 問題を構造化できる人
- 現場とデータをつなげられる人
- 分析から次アクションまで設計できる人
- このプロジェクトを前に進めるために残すべき人

## 今日の作業方針

今日の作業は、見た目の完成度だけを追わない。  
自分の設計力が伝わるように、以下を揃える。

- 利用率低下の分解フレーム
- 入力項目の定義
- 4か月分データを入れられるCSV形式
- 集計・可視化の画面
- 仮説表示
- 次アクション候補
- 明日以降の検証手順

これにより、成果物だけでなく、自分が継続して関わる理由を作る。
