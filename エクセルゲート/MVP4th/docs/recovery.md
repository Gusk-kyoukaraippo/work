# 中断・障害・管理者復旧

## 正式保存の段階

1. 受け渡しを検証し、`data/.pending` に原本をコピーして照合します。
2. **現在の正式データ・revisionを変えずに**、次版・原本パス・セッション・履歴PREPAREDをブックへ保存します。
3. `data/accepted/yyyy-mm` へ原本を公開します。同名で内容が違う場合は上書きしません。
4. 新データ・SUCCESS履歴・次revisionをメモリ上で設定して、最後のブック保存を実行します。失敗時はDATA・META・HISTORYの保存前の内容を復元します。
5. 最後の保存成功後だけpendingを削除し、終了出力ならセッション補助ファイルも削除します。共有ファイルの編集権は**ブックを閉じるまで**保持します。

CRC32と文字数は事故による破損の確認です。悪意ある改ざんを防ぐ署名やアクセス権管理ではありません。

## 利用者が再試行できる場合

「正式保存が未完了です」と表示されたら、ブック・元のHTML・受け渡しJSONを保持し、共有フォルダの接続を確認して「受け渡しファイルを正式保存する」を再実行します。PREPAREDなら同じ処理を再開し、新しい出力を探しません。HTML側で必要なのは同じ受け渡しの再出力であり、保存者名や内容を変えて出し直す必要はありません。

最後の保存に失敗しても、同じブック内で旧データ・旧revision・PREPAREDを保持するよう実装しています。ディスクにPREPAREDが保存されていれば再起動時にも再開します。最初のPREPARED保存前に異常終了した場合は、次の起動へ編集権を持ち越しません。残った原本からの救済が必要なら管理者手順を使います。

PREPAREDが解決しない場合、通常の終了操作はブックを閉じません。pendingを手作業で消したり、SUCCESSへ書き換えたりしないでください。共有フォルダへの書き込み失敗がブックそのものを破損させた場合まで、メモリ上の巻き戻しで修復できるわけではありません。フォルダ全体のバックアップと次の管理者手順が必要です。

## 保全した原本から新しい正本を作る

1. 利用者全員の編集を止め、旧正本、`data`、ダウンロード中の受け渡し、一時実行フォルダを日時付き別フォルダへ保全します。旧正本を上書きしません。
2. 旧ログのSUCCESSと対応する `accepted` のJSONを選びます。`accepted` にあることだけでは最終ブック保存の成功を意味しません。PREPARED中の原本を救済する場合は、その内容と採用可否を管理者が確認します。
3. 同じアプリ・dataVersionの配布一式を新しい正本の最終場所へ置き、導入手順で共通VBAを組み込んだ未使用 `MVP4th.xlsm` に `InitializeGate` を実行します。
4. 管理者が `GateAdminRestoreAccepted` を実行し、保全したJSONを選びます。表示される元データID・出力者・アプリ・ファイルを確認して実行します。
5. 元のJSONは `data/backups/recovery-source-*.json` に保全されます。新しいデータID・セッションの外枠へ業務payloadを移し、通常と同じ正式保存処理を通します。元の正本の履歴は旧バックアップに残り、新正本はrevision 1から始まります。
6. 新正本を閉じて開き直し、閲覧で内容を確認します。二台で排他を試験した後、全利用者に新しい正本の同じUNCパスを案内します。古いHTMLと受け渡しは、新正本の通常保存では拒否されます。

復旧マクロは初期化直後の空正本だけを受け付けます。任意の旧JSONを通常保存へ入れる抜け道は設けません。復旧時の最後の保存が中断した場合もPREPARED再開を使用します。保存前段階で失敗した空の復旧先は、証跡を残して別の新品からやり直せます。

## 保存失敗を再現する試験用フック

実データのない試験用配布コピーだけで、`GateDeployment` の `#Const GATE_TESTING = False` を `True` に変更し、`tests/windows/GateFailureTests.bas` を追加インポートします。`GateRunFailureTests` は試験データを作成して正式保存を繰り返すため、本番正本で実行しません。

フックはpending、PREPARED保存、accepted公開、最終ブック保存の直前に一度だけエラーを発生させます。元データ・版・PREPARED・セッション・pendingの維持と、同じプロセスでの再試行後に版が一度だけ進むことを確認します。これは実際の通信断・ディスク満杯・ファイルサーバー障害を模擬する完全な試験ではありません。再起動と二台試験は `acceptance-test.md` で別に実施してください。配布版のフックは無効です。
