# 病床管理アプリ 構想・要件整理

## 1. 文書の目的

本書は、現在JUST Calcで運用している病床管理表をもとに、現場の操作感を大きく変えずに業務を改善し、将来的なデータ活用と院内Webシステム化につなげるための構想・要件を整理したものである。

今回の開発は完成形の院内システムではなく、`file://`環境で動作する実証版を作り、病床調整とデータ活用の有効性を示すことを第一段階とする。

---

## 2. 現在の運用

- JUST Calcを使用し、共有フォルダ上のExcel形式ファイルで管理している。
- 縦方向に病室・ベッド・患者、横方向に日付を配置した、方眼紙状の病床表である。
- 患者の入院期間を横方向のセル着色で表現している。
- 入院区分は背景色で識別している。
- 病床表には患者名、主治医、疾患、入院期間、転床・退院予定、注意事項等が記載される。
- 表の下部に、ベッド数、稼働率、入院件数、退院件数等の集計欄がある。
- 新規患者、定期利用者、キャンセル者、終了者、事前同意等を別シートでも管理している。
- 複数職員が利用するが、厳密な同時編集対応は現時点では重視しない。

### 入院区分と色

| 入院区分 | 表示色 |
|---|---|
| レスパイト | 青 |
| リハビリ | 灰色 |
| 長期入院 | ピンク |
| 通常入院 | オレンジ |

色は患者固有ではなく、入院区分を表す。

## 3. 現状の課題

### 3.1 病床調整上の課題

- ある日付の病棟全体の稼働率や空床数を即座に把握しにくい。
- 男性部屋・女性部屋を考慮した空床候補を探しにくい。
- 将来の入院予定を見ながら、効率のよいベッド移動を検討しにくい。
- 入院・退院が集中する日を把握しにくい。
- 転床前後の履歴を構造的に追跡できない。
- 未配置の入院予定と、配置済みの患者を一元的に扱いにくい。

### 3.2 データ活用上の課題

- 患者名、疾患、期間、補足情報等が一つのセル内で文章として混在している。
- セルの位置と背景色自体が意味を持っており、機械的な集計が難しい。
- 入院履歴が「初回入院日」「2回目入院日」「3回目入院日」のように横へ増える構造になっている。
- 同じ患者の4回目以降の入院や、入院ごとの区分・退院日・病床移動を扱いにくい。
- 予定日と実績日が明確に分離されておらず、予測精度や計画差を検証しにくい。
- 日別の入退院件数等に手入力が含まれ、再利用可能な元データになっていない。
- 現行ブックは書式情報の肥大化等により約68MBあり、保守性が低い。

### 3.3 表計算ソフトを拡張する場合の限界

- JUST CalcやExcelのセル構造を改良しても、表示とデータが同じ場所にある問題が残る。
- マクロや書式への依存が増えるほど、互換性と保守性の問題が大きくなる。
- 将来的な検索、履歴管理、予測、他システム連携へ発展させにくい。

## 4. 目的

### 4.1 第一段階の目的

- 現在のExcel表に近い見た目と操作感を維持する。
- 患者登録、入院予定、病床配置、期間変更、転床を簡単にする。
- 日別稼働率、空床数、男女別空床等を自動集計する。
- 将来の入院予定を視覚的に把握できるようにする。
- 入力内容を集計可能な構造化データとして蓄積する。
- 現場に実際に使用してもらい、院内サーバー化の効果を説明できる成果を作る。

### 4.2 将来的な目的

- 院内ネットワーク上のWebアプリへ移行する。
- 複数端末から常に同じ最新データを参照できるようにする。
- 認証、権限、変更履歴、バックアップを整備する。
- 蓄積データを病床運用の予測と意思決定に利用する。

## 5. 所与要件・制約

### 5.1 実行環境

- アプリは当面、`file://`から起動する。
- 院内サーバーの設置は現段階では前提にできない。
- インターネット接続や外部クラウドサービスに依存しない。
- 複数職員が利用する。
- 厳密なリアルタイム同時編集や競合解決は、今回の必須要件にしない。

### 5.2 ファイル構成

- アプリ本体は単一のHTMLファイルとする。
- JavaScriptとCSSはすべてHTMLファイル内に記載する。
- 外部CDNや外部JavaScriptへの依存を避ける。
- アプリ本体とは別に、共有用のJSONデータファイルを使用できる。

### 5.3 使用禁止機能

- IndexedDBは使用しない。
- File System Access APIは使用しない。
- ブラウザから共有フォルダのファイルを自動上書きする設計にはしない。

### 5.4 使用可能なブラウザ機能

- 標準のファイル選択欄（`input type="file"`）によるJSON読込。
- BlobとダウンロードリンクによるJSON・CSV出力。
- `localStorage`による端末内の作業中データ・復旧用データの保存。

`localStorage`は共有データの正本とはせず、操作中の自動保存と障害復旧に限定する。

## 6. 基本方針

### 6.1 見た目はExcel、内部はデータベース型

利用者が触る画面は現在の病床表に近づける。一方、内部ではセルの色や文章をデータとして保存せず、患者、入院、病床、病床割当を別々のデータとして管理する。

### 6.2 色は保存値から生成する

入院区分を文字列またはコードとして保存し、その値に応じて画面上の色を自動決定する。色そのものをデータの意味として扱わない。

### 6.3 表示と保存処理を分離する

初期版ではJSONを読み書きするが、将来は同じ画面から院内APIを利用できる構造にする。

```text
病床ボード・患者リスト・集計画面
                  ↓
            データ保存窓口
             ↙          ↘
       今回：JSON     将来：院内API
```

## 7. 画面構成

### 7.1 左側：病床ボード

- 縦方向に病室とベッドを表示する。
- 横方向に日付を表示する。
- 患者の滞在期間を横長の帯として表示する。
- 入院・退院・転床は分単位の日時で管理するが、月間表では日単位の横幅に収まるよう簡略表示する。
- 同じ日に退院、病床整備、新規入院がある場合は、該当セルに入替マークまたは境界線を表示する。
- 入替マークへマウスを重ねると「09:00退院／09:00～10:00整備／10:00入院」のように表示する。
- 日付または入替マークを選択すると、その日の入退院・転床・病床整備を時間軸で確認できる詳細表示を開く。
- 帯の背景色は入院区分を表す。
- 今日の列、土曜日、日曜日、祝日を視認しやすくする。
- 病室・ベッド欄と日付行はスクロール時も固定する。
- 月単位または複数月を横スクロールして確認できるようにする。

### 7.2 右側上段：CPから追加

- CPは当院における患者IDとして扱う。
- CPを入力して患者を検索する。
- 登録済みの場合は、氏名、性別、最終入院日等を表示する。
- 未登録の場合は、新規患者として必要項目を登録できるようにする。
- 入院区分、入院予定日時、退院予定日時または予定日数を入力する。
- 登録後は、病床未配置の入院予定として扱う。

### 7.3 右側中段：配置待ち患者

- 入院日程は決まっているが、病室・ベッドが未定の患者を表示する。
- CP、氏名、性別、入院区分、予定期間、運用上の注意事項を表示する。
- 患者を病床ボードへドラッグして配置できるようにする。
- ドラッグ以外に、フォームから病室・ベッドを指定する操作も用意する。

### 7.4 右側下段：常連患者

- 患者台帳で「常連」と指定された患者を対象とする。
- 表示中の月に入院実績または入院予定がない患者だけを表示する。
- CPまたは氏名で検索できるようにする。
- 最終入院日を表示し、新しい順等で並べ替えられるようにする。
- 当月の予定を登録した患者は一覧から自動的に除外する。
- 一覧は折り畳み可能とする。

### 7.5 上部：サマリー

- 表示日時または現在時刻の使用床数、空床数、稼働率。
- 当日の時間帯別の使用床数・空床数の推移。
- 稼働床数と空床数。
- 男性用・女性用・調整可能な空床数。
- 入院予定件数と退院予定件数。
- 警告件数。
- 読み込んでいるデータの保存日時、保存者、バージョン。
- 未保存変更の有無。

## 8. 主な操作要件

- 右側の患者を病床ボードへドラッグして配置する。
- 入院帯の左右端を操作し、入院期間を変更する。正確な時刻は詳細編集で指定する。
- 入院帯を上下に移動し、転床を登録する。
- 入院・退院・転床・病床整備・受入可能時刻は分単位で登録する。
- 退院時刻と、その病床へ次の患者を受け入れ可能になる時刻を分けて管理する。
- セルまたは入院帯のダブルクリックから詳細編集を開く。
- 右クリックまたは操作メニューから、退院、転床、取消等を選択する。
- 直前の操作を元に戻せるようにする。
- 誤操作を防ぐため、重要な変更は確定前に変更内容を表示する。
- 同一患者の時間帯重複、同一ベッドの時間帯重複、病床整備中の配置、定員超過等を警告する。
- 色だけに依存せず、入院区分名、枠線、警告アイコン等も併用する。

### 日付の簡易入力

次のような入力を補助的に解釈できるようにする。

- `1か月後から2週間`
- `8月1日から14日間`
- `来週月曜から10日`
- `8/1〜8/14`
- `7/13 10時から7/27 9時まで`

解釈後は、確定前に実際の日時範囲を表示する。時刻が省略された場合の初期値は別途設定し、利用者が確定前に変更できるようにする。初期版では通常の日付・時刻欄と日数欄を基本操作とし、文章入力はショートカットとして扱う。

## 9. データ構造

### 9.1 患者

| 項目 | 内容 |
|---|---|
| patientId | アプリ内の一意ID |
| cp | 当院患者ID。文字列として保存 |
| name | 氏名 |
| sex | 男性・女性・その他運用上必要な区分 |
| regular | 常連フラグ |
| operationalNotes | 病床調整に必要な最小限の注意事項 |
| active | 利用中・終了等 |

### 9.2 入院

1回の入院につき1件作成し、入院回数に応じて列を増やさない。

| 項目 | 内容 |
|---|---|
| admissionId | 入院ごとの一意ID |
| patientId | 患者ID |
| admissionType | レスパイト・リハビリ・長期・通常 |
| plannedAdmissionAt | 入院予定日時（分単位） |
| plannedDischargeAt | 退院予定日時（分単位） |
| actualAdmissionAt | 実入院日時（分単位） |
| actualDischargeAt | 実退院日時（分単位） |
| status | 予定・入院中・退院・キャンセル |
| changeReason | 延長・短縮・キャンセル等の理由 |

予定日と実績日を分けて保存し、将来の計画精度を検証できるようにする。

### 9.3 病床

| 項目 | 内容 |
|---|---|
| bedId | 病床の一意ID |
| roomNumber | 病室番号 |
| bedNumber | 病室内のベッド番号 |
| roomRule | 男性・女性・調整可能等 |
| roomType | 個室・多床室等 |
| available | 使用可能・閉床等 |

### 9.4 病床割当

| 項目 | 内容 |
|---|---|
| assignmentId | 割当の一意ID |
| admissionId | 入院ID |
| bedId | 病床ID |
| fromAt | 使用開始日時（分単位） |
| toAt | 使用終了日時（分単位） |

転床時は既存の入院を上書きせず、同じ入院に新しい病床割当を追加する。

日時区間は開始時刻を含み、終了時刻を含まない`[fromAt, toAt)`として扱う。例えば前患者の使用終了が10:00、次患者の使用開始が10:00であれば、時間帯の重複とは判定しない。

### 9.5 病床利用不可区間

退院後の清掃・整備や、一時的な閉床を患者の病床割当とは別に記録する。

| 項目 | 内容 |
|---|---|
| blockId | 利用不可区間の一意ID |
| bedId | 病床ID |
| fromAt | 利用不可開始日時（分単位） |
| toAt | 受入可能日時（分単位） |
| reason | 清掃・整備・修繕・一時閉床等 |

退院時刻と受入可能時刻が同一でない場合は、その間を病床利用不可区間として表示する。次の患者の入院予定日時が受入可能時刻より前の場合は警告する。

### 9.6 変更履歴

| 項目 | 内容 |
|---|---|
| logId | 履歴ID |
| changedAt | 変更日時 |
| changedBy | 変更者 |
| entityType | 患者・入院・病床割当等 |
| entityId | 対象ID |
| action | 追加・変更・削除 |
| before | 変更前の値 |
| after | 変更後の値 |

初期版では厳密な認証を行わないため、利用開始時に担当者名を選択または入力する方式を想定する。

## 10. 自動集計・警告

### 10.1 初期版で実装を目指す集計

- 日別の使用床数、空床数、稼働率。
- 指定時刻時点の使用床数、空床数、稼働率。
- 時間帯別の使用床数・空床数の推移。
- 月平均稼働率。
- 男女別の利用可能病床数。
- 日別の入院予定件数、退院予定件数、転床件数。
- 入院区分別の患者数と病床日数。
- 病床ごとの使用時間、空床時間、退院から次回入院までの回転時間。
- 将来2週間・1か月程度の空床見込み。

### 10.2 警告

- 同一ベッドの時間帯重複。
- 同一患者の入院時間帯重複。
- 病床整備・清掃・一時閉床中の配置。
- 病室定員超過。
- 男女部屋ルールとの不一致。
- 閉床中ベッドへの配置。
- 入院日時と退院日時の逆転。
- 退院日時より受入可能日時が前になる不整合。
- CP未設定または重複。
- 入院・退院件数が設定した上限を超える日。

稼働率の分母は固定値にせず、対象日時に使用可能な病床数とする。閉床・清掃・整備中のベッドの扱いは、病床調整用指標と正式な院内統計の定義を分けて設定できるようにする。

### 10.3 将来的に取得したい指標

- 予定期間と実入院期間の差。
- 入院延長率、短縮率、キャンセル率。
- 入院区分別の平均入院日数。
- 常連患者の利用間隔。
- 転床回数と転床理由。
- 退院から病床受入可能までの整備時間。
- 病床受入可能から次回入院までの空床時間。
- 時刻別の入院・退院・転床集中状況。
- 入退院が集中する曜日・時期。
- レスパイト利用等の季節傾向。
- 将来空床予測の精度。

## 11. JSON運用

### 11.1 ファイル

- アプリ本体：`bed-control.html`
- 共有データ正本：`bed-control-current.json`
- バックアップ例：`bed-control-20260712-173500-v0128.json`

### 11.2 基本運用

1. 共有フォルダの`bed-control.html`を開く。
2. 「共有データを開く」から`bed-control-current.json`を選択する。
3. 担当者名を選択または入力する。
4. 病床表を編集する。
5. 「共有データを保存」から更新済みJSONをダウンロードする。
6. 共有フォルダの`bed-control-current.json`を更新する。

### 11.3 JSONに持たせる管理情報

- データ形式のバージョン（schemaVersion）。
- 運用データの通し番号（revision）。
- 保存日時。
- 保存者。
- アプリのバージョン。
- 患者、入院、病床、病床割当、病床利用不可区間、変更履歴。

### 11.4 安全対策

- 読み込んだJSONの形式と必須項目を検証する。
- 古いデータ形式は読込時に変換する。
- 読込中のデータより古いrevisionを保存しようとした場合は警告する。
- 未保存変更がある状態で画面を閉じる場合は警告する。
- `localStorage`へ作業中データを自動保存する。
- JSON保存時にバックアップ用ファイルも生成できるようにする。
- JSON全体を置き換える前に、現在の正本をバックアップする運用とする。

同時編集を完全には防げないため、初期版では「利用前に最新JSONを読み込み、利用後に速やかに保存する」という運用ルールで補う。

### 11.5 データ肥大化対策

- 画面上の日付セルや色付きマス目をJSONへ保存せず、入院・病床割当・利用不可区間から表示時に生成する。
- 画像、PDF等の添付ファイルや、病床調整に不要な長文の診療情報をJSONへ格納しない。
- 通常使用する`bed-control-current.json`には、患者・病床マスター、現在の入院、将来予定、直近の履歴を保持する。
- 終了済みの古い入院・病床割当・変更履歴は、年度別の`bed-control-archive-YYYY.json`へ退避できるようにする。
- 過去分析時には複数の年度別JSONをまとめて選択し、画面上で一時的に結合して集計できるようにする。
- JSONのファイルサイズ、患者件数、入院件数、変更履歴件数を画面に表示する。
- 10MB超で注意、20MB超でアーカイブを提案、50MB以上は分割を必須とする運用基準を初期値とし、実際の院内PCでの検証結果に応じて調整する。
- `localStorage`は全期間のデータ保管先にせず、現在の作業データまたは直近の復旧データに限定する。

## 13. 初期版の実装範囲

### 必須

1. 単一HTML・`file://`での起動。
2. 現行表に近い病床×日付ボード。

## 14. 移行方針

### 段階1：実証版

- 単一HTML＋共有JSONで作成する。
- 匿名化または必要最小限のデータで操作検証する。
- 現在のExcel表に近い画面を再現する。
- 稼働率、将来空床、男女部屋、入退院集中日の可視化を行う。

### 段階2：並行運用

- 一定期間、現行JUST Calcと実証版を並行使用する。
- 操作時間、入力ミス、集計時間等を比較する。
- 実際に必要な項目と不要な項目を整理する。
- JSON交換の手間を記録する。

### 段階3：院内サーバー化の提案

実証結果をもとに、以下を説明する。

- 画面と集計機能はすでに有効性を確認済みであること。
- 残る主な課題はJSONの手動交換であること。
- 院内サーバー化すれば、同じ画面のまま共有保存、最新版参照、認証、バックアップを自動化できること。
- サーバー化は全面的な作り直しではなく、データ保存部分の置き換えで対応できること。

### 段階4：院内Webアプリ

- 院内URLから起動する。
- JSON保存処理をAPIとデータベースへ切り替える。
- 認証、アクセス権、監査ログ、バックアップを追加する。
- 必要に応じて電子カルテ等との連携を検討する。

## 16. 医療情報としての注意点

- 患者名、CP、入院履歴は個人情報・医療関連情報として扱う。
- 病床調整に不要な詳細な診療情報は、原則として本アプリに保存しない。
- 自由記述欄には、病床調整に必要な最小限の情報のみ入力する。
- HTML、JSON、バックアップはアクセス制限された院内共有フォルダに置く。
- 個人端末のダウンロードフォルダにJSONを残さない運用を検討する。
- `localStorage`に実患者データを保存する場合は、共用端末の管理方法とブラウザデータ削除方針を確認する。
- 実証段階では可能な限り匿名データまたは仮データを使用する。

## 18. 現時点の推奨結論

今回の実装は、以下の方針で進めるのが適切である。

1. `file://`、単一HTMLという条件を維持する。
2. 共有データは構造化JSONを正本とし、`localStorage`は復旧用とする。
3. 見た目と基本操作は現在のExcel病床表に近づける。
4. 内部では患者、入院、病床、病床割当、変更履歴を分離する。
5. 初期版で日別稼働率、将来空床、男女部屋、入退院集中等の効果を示す。
6. JSON手動交換の負担を実測し、それを院内サーバー化の根拠とする。
7. 将来は画面を作り直さず、保存処理だけを院内APIへ交換できる設計にする。

この実証版の価値は、単に現在の表を操作しやすくすることではなく、病床運用を将来分析できるデータへ変換し、次の院内システム化へつなげることにある。
