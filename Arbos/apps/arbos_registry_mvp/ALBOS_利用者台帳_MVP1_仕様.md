# ALBOS 利用者・利用調整台帳 MVP1

更新日：2026年7月19日

## 目的

ロング、ショート、デイに分かれている利用者情報を、患者IDを正式キーとして一人単位で一元把握する。

本台帳は診療録・介護記録や既存システムを複製するものではない。「どのサービスを利用しているか」「直近の利用と次回予定はいつか」「誰が何を確認しているか」「次にいつ確認するか」を短時間で俯瞰し、利用調整とフォロー漏れ防止に使う。

## 固定する運用制約

- アプリはCSS・JavaScriptを内包した単一HTMLとする。
- `file://` で直接開き、Webサーバーを必要としない。
- インターネット通信、外部ライブラリ、外部画像、外部フォントを使用しない。
- IndexedDB、File System Access API、localStorage、sessionStorageへ利用者情報を保存しない。
- 読込は通常のファイル選択、保存は全量JSONのダウンロードとする。
- 読込元JSONを直接上書きしない。
- 書き出したJSONは、アプリへの再読込確認が終わるまで未検証の正本候補として扱う。
- 初期版は中央管理担当者が正本JSONを排他運用する。

## MVP1で実現すること

### 1. 今週のフォロー

- 期限超過、本日期限、7日以内、期限未設定、予約化を集計する。
- 氏名、患者ID、フォロー区分、状態、担当者、期限で絞り込む。
- ショート再利用、ロング相談、デイから初回ショート、退所後、3F候補等を同じ構造で管理する。
- 対応結果と次回確認日を記録し、関連フォローの状態・期限を更新する。

### 2. 利用者台帳

- 1利用者1行で表示する。
- 患者ID、氏名、利用サービス、直近実績、次回予定、主担当、次回確認、3F適合確認を横断表示する。
- ロング、ショート、デイ、台帳状態、フォロー有無、3F適合確認で絞り込む。
- 同姓同名でも患者IDが異なれば別利用者として保持する。

### 3. 利用者詳細と統合時系列

- 基本情報、主担当、ケアマネ、最新フロア、3F適合確認を表示・更新する。
- サービスごとに利用中・休止・終了・未確認、頻度、担当、最終確認日を保持する。
- 実績、予定、取消と、電話・家族・ケアマネ・院内確認等の調整記録を同じ時系列に表示する。
- 未完了フォローと次の行動を一画面に表示する。

### 4. JSON正本管理

- JSON読込時にschemaVersion、重複患者ID、孤児参照、サービス参照、フォロー参照を検証する。
- 破損または不整合のあるJSONは読み込まず、現在の作業データを維持する。
- 保存前にも全件検証する。
- 保存時にrevisionを1増やし、previousRevision、保存日時、操作担当者を記録する。
- 保存時は読込元を上書きせず、新しい全量JSONをダウンロードする。
- 書き出したJSONは再読込され、検証結果、主要件数、revisionが確認されるまで未検証とする。
- データ元ごとに最新データ日と連携状態を保持する。

### 5. データ管理画面

- 現在開いているdataset、revision、保存日時、操作担当者、主要コレクション件数を表示する。
- 元データごとの最新データ日、実取込日時、手動確認日時、連携状態を表示・更新する。
- HTML上で行った変更履歴を直近分から確認する。

## データ設計

| コレクション | 役割 |
|---|---|
| `users` | 患者ID、氏名、台帳状態、主担当、ケアマネ、最新フロア、3F確認 |
| `serviceCatalog` | ロング、ショート、デイ、将来追加するサービス定義 |
| `serviceRelations` | 利用中・休止・終了、頻度、担当、最終確認日 |
| `serviceEvents` | 利用実績、予定、取消、期間、フロア、情報源 |
| `followupTasks` | 区分、状態、職員判断の優先度、担当、期限、理由、次の行動 |
| `coordinationRecords` | 対応日、方法、相手、結果、記録、次回確認日 |
| `sourceFreshness` | データ元、最新データ日、連携状態、取込日時、注意事項 |
| `changeLogs` | HTML上で行った変更の作業記録 |

## 患者IDと参照の原則

- `patientId` は必須の文字列とし、先頭ゼロを保持する。
- 氏名だけでは利用者を統合しない。
- 内部参照には変更されない `userId` を用いる。
- 患者IDは登録後に通常画面から変更しない。
- 利用者を物理削除せず、休止またはアーカイブへ変更する。
- 未完了フォローがある利用者はアーカイブできない。先にフォローを完了または引き継ぐ。

## 実績・予定の原則

- `actual`、`planned`、`cancelled` を区別する。
- 最終利用日、次回予定、未完了件数は画面表示時に計算し、利用者行へ重複保存しない。
- 予定表が連携済みで将来予定がない場合だけ「次回予定なし」と表示する。
- 予定表が未連携または一部連携の場合は「予約情報未連携」と表示する。
- 医学的・介護的な受入可否や3F適合をシステムが自動確定しない。

## 正本JSONの運用

1. 中央管理場所から最新revisionの正本JSONを作業端末へ用意する。
2. HTMLを開き、正本JSONを読み込む。
3. 操作担当者を入力して更新する。
4. 未保存表示を確認し、JSON保存を実行する。
5. 出力直後のJSONを未検証の正本候補として扱い、まだ正本へ差し替えない。
6. 出力JSONを同じHTMLへ再読込し、検証に通ることと、利用者数・履歴数・revisionを確認する。
7. 旧正本をバックアップしてから、確認済みの新JSONを正本へ差し替える。
8. ダウンロードフォルダに残った個人情報JSONを院内規程に沿って整理する。

「JSON保存」ボタンの実行やダウンロード完了だけを、正本の保存完了とはみなさない。アプリが書き出し先を直接検証できないため、再読込確認を運用上の必須手順とする。

## 初期JSON作成スクリプトの位置づけ

`build_initial_registry_json.py` は、既存のSQLite分析DBから運用開始前の初回読込用JSONを生成する準備ツールである。ブラウザでの本運用には使用せず、稼働中の正本JSONを更新・追記・統合する用途にも使用しない。

- 出力先は、まだ存在しない新しいファイルパスに限る。
- 同名ファイルが存在する場合は上書きせず終了する。
- フォロー記録や調整記録を持つ既存正本を入力または出力先にしない。
- 患者IDへ未照合のデイ利用者を氏名だけで自動統合せず、除外件数を警告する。

## 解決した障害

- サービス別に分かれていた情報を患者ID中心の構造へ統合した。
- 週次CSVで途切れていたフォロー状態と次回確認日をJSONへ永続化できるようにした。
- 「予定なし」と「予定情報未連携」を分けた。
- 氏名だけの自動統合を行わず、患者IDを必須にした。
- 制限環境でも、通常のファイル選択とJSONダウンロードだけで読込・保存できるようにした。
- 外部通信、ブラウザDB、自動保存への依存を除いた。

## 残る運用上の障害

- 共有サーバー、ロック、競合検出、差分マージがないため、同じ正本JSONを複数人が同時編集すると変更競合を防げない。
- 初期版は中央管理担当者1人が、最新revisionの受渡し、編集、再読込確認、正本差替えまでを排他的に行う必要がある。
- 複数部署が別々に編集したJSONを、アプリ上で自動統合することはできない。
- JSONは平文の個人情報であり、OS権限、端末暗号化、バックアップ、ダウンロード残骸管理が必要である。
- 操作者名と変更履歴は作業記録であり、認証や改ざん防止を備えた正式監査ログではない。
- 現在のデイ実績には患者IDへ未照合の利用者が存在する。患者ID付きデータへ切り替えた後に初期JSONを再作成する必要がある。
- 元データの更新担当、更新頻度、正本差替え責任者は院内運用として別途固定する必要がある。

## MVP1に含めないもの

- 部屋割り、送迎、完全な予約管理
- 複数人の同時編集
- ログイン・権限管理
- 自動架電・自動連絡
- 自動優先順位、自動受入判定
- 既存システムへの書き戻し

## 成功条件

- 同一患者IDのロング、ショート、デイを重複なく1人として表示できる。
- 利用者詳細を開けば、利用関係、直近実績、次回予定、未完了フォロー、対応履歴を確認できる。
- 対応結果と次回確認日を記録し、保存JSONの再読込後も維持できる。
- 書き出したJSONを未検証として扱い、再読込による検証と件数・revision確認後だけ正本へ差し替える。
- 破損JSON、重複患者ID、孤児参照を拒否できる。
- ネットワークなしの `file://` 環境で主要操作が完結する。
- HTMLに外部通信処理や禁止された保存APIが含まれない。
