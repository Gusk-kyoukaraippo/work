# このUIが成立する条件

利用者へ受け渡しの概念を教える代わりに、状態に合った次の操作をその場に表示します。正式保存が終わるまで、完了と案内しないことが前提です。

## A：通常UI

既存の出力とブックの保存処理を使います。Edgeでは開いているブックの「保存して閉じる」へ誘導し、ブックの正式保存が成功してから「Edgeの作業タブを閉じてからOK」の案内を出します。最後のOKまでブックを開き、両方を閉じる順番を示します。

利用者はダウンロードの完了を判断しません。受け取りがまだ間に合わなければ、ブック側で待って同じ保存ボタンを押す案内を出します。技術を追加する量は少なく、画面の行き来は残ります。

## B・C：準備完了をEdgeに知らせる

1. ブックが、現在の編集作業の終了データを探します。
2. ブック・作業ID・データ版・起点のリビジョン・出力順序を照合します。途中出力から終了出力まで、未保存のつながりも検証します。
3. 一式を共有側の一時保管場所にコピーし、読み直して検証します。
4. ここまで成功した場合だけ、ローカルのJavaScriptファイルへ今回の準備完了通知を出します。
5. Edgeの起動ページが約1秒ごとに通知を読み、今回の終了データと一致した場合だけ「保存の準備ができました」へ切り替えます。
6. Edgeを閉じた後、ブックの「保存して閉じる」が保管済みデータを正式保存し、履歴を確定してブックを閉じます。

準備完了は、正式保存の完了ではありません。正式保存に失敗した場合は保管済みデータを残し、既存のPREPAREDからの再開処理を使います。保存後に閉じる処理だけ失敗した場合は再取込をせず、閉じる操作だけ再試行します。

終了データの再出力は、作業ID・順序・内容を変えない同じ出力です。別の作業の通知や、古い終了出力の通知は準備完了として扱いません。ローカルスクリプトで通知を読むため、常設サーバーや追加の利用者用ソフトは不要です。

## BとCの違い

Bはブックに属するApplication.OnTimeを約1秒ごとに予約します。次回実行は前回の確認後に予約し、停止・閉じる際は同じ日時と処理名で取り消します。JUST Calcがこの予約をEdge操作中にも実行するかを実機で確かめます。

Cは編集開始のVBAを待機させ、DoEventsとWindows標準Sleepの短い待機を挟んで約1秒ごとに確認します。受け取り中と保存中の再入を止めます。途中保存のクリックは待機終了後に処理し、編集が続く場合は待機を再開します。中断時は「終了の準備を再開」を案内します。JUST Calcの操作感、キャンセル、CPU負荷を実機で確かめます。

Mac版Excelのコンパイルとブラウザ試験で、Windowsの受け取り・共有ロック解除・VBA待機の性能は保証できません。3案を同じ業務画面で試し、迷いと実機の成否を分けて記録します。
